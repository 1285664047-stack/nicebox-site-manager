# 修改已有文章

本流程只修改已有文章业务数据，不修改页面模板。通信方式与回退过程保持静默。

## 定位与确认

1. 用户提供编号时精确查询；只提供名称时模糊搜索。存在多条结果时展示候选并让用户选择，禁止自行猜测。
2. 选定文章后读取完整详情，保留返回的一致性摘要供写入使用，不向用户显示该摘要。
3. 允许单独或一次修改多个字段：标题、摘要、文章类型、外链、分类、语言、封面、正文、作者、来源、来源链接、FAQ、发布时间、显示状态、排序、SEO 标题、SEO 关键词、SEO 描述、Schema、文件名、详情页和浏览量。
4. 展示“当前值 -> 新值”的修改摘要，只列本次字段；取得一次明确确认后直接保存。参数变化后重新确认。
5. 文件名变化时先检查当前账号其他文章。存在同名时停止保存并提示更换；不检查产品和页面。
6. 分类和详情页只能使用查询得到的真实 ID；图片先按素材规则上传，再使用返回地址。

## 保存后的分支

- 服务端只更新用户明确提供的字段。内容已被其他操作修改时重新读取、重新展示差异并重新确认，禁止覆盖。
- 修改 `faq_items` 时，服务端自动同步 `schema_json_ld`，不再询问是否同步。
- 正文发生变化且本次没有修改 SEO 四项时，保存后询问是否重新生成 SEO。用户确认后完整覆盖 `seo_title`、`seo_keywords`、`seo_description`、`schema_json_ld`；确认提示不提 Token 消耗，不做补空，不处理图片 Alt。
- 只有修改前已经存在 FAQ、正文发生变化且本次没有修改 FAQ 时，保存后询问是否重新生成 FAQ。原来没有 FAQ 时不询问、不自动生成。
- SEO 与 FAQ 都需要询问时一次提供“都生成 / 仅 SEO / 仅 FAQ / 都不生成”。同时生成时先生成 FAQ，再基于最新文章状态生成 SEO，每次使用上一步返回的新一致性摘要。
- 所有重新生成都必须等待用户确认；后台仍记录 Token 消耗和请求来源，但不得在提示文案中提及 Token 消耗。

## 用户输出

只报告本次文章实际修改字段和保存结果。需要后续生成时只展示业务选项，不显示内部参数、摘要、接口或执行方式。
